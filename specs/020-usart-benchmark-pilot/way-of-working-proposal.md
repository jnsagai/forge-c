# Way-of-working proposal for future modules

Generated by `forge_factory.benchmark.proposal` from the pilot decision log, its classification and the benchmark comparison. Every rule cites its decision-log entry; the evidence is in the log.

## Default rules

- A private reference project is used for its process and numeric metrics only; its content never enters the repository (D1)
- Delivered vendor code stays frozen; the factory generates the ASPICE work products around it and reports findings instead of edits (D2)
- One module per peripheral driver (its HAL and LL components) under one requirement set (D3)
- A component the delivered HAL does not call is a second public API with its own functional requirements (D4)
- SWE.1 states functional/API behaviour; register-level detail and concrete negative paths are specified at SWE.3 (D5)
- The factory generates and coverage-checks the governance package (input register, actors, use cases, open points); no sign-off; the owner may add use cases (D7)
- Requirement quality keeps the two-phase per-requirement and set inspection criteria unchanged (D9)
- Every mechanism is module-agnostic; module facts are order data, and a second module needs no code change (D10)
- The inventory and scope classification are deterministic in prepare; actors and use cases come from a model step with a deterministic coverage check (D11)
- The functional-level role text is a versioned skill reference rendered by the registry generator; the role skill stays unchanged (D15)
- Governance step and coverage check run before the SWE.1 author; an uncovered in-scope function stops SWE.1 (D16)
- Scope patterns resolve exact name before longest pattern; ties are input gaps; delivered code and conversion provenance are never sources (D17)
- The functional author plans one bounded task per service group of the scope rule, one state-behaviour task and one design-constraint task per guideline part (D18)
- The author answer is schema-checked; conditional template rules, links to the input register, the level rule and EARS are deterministic validators, the same per task and at the gate (D19)
- The level-rule vocabulary comes from the order's reference-manual register sections and the device header symbols of the module's register prefixes (D20)
- A functional order always gets a structured SWE.1 with the two-phase inspection, independent of the local profile (D21)
- The set inspection of a functional order uses functional notes and the governance package as its source; criteria unchanged (D23)
- A guideline larger than the packet bound is split at headings into consecutive parts, each its own design-constraint task; never truncated (D24)
- The device header is an order input (level-rule term source) held in the inputs cache by digest; the delivery scope lists every function the delivered headers declare (D25)
- A new module runs as a pilot lineage on its own phases, after the ready ladder steps and without reordering or chaining the ladder (D26)
- A new owner-lane lineage needs no policy grant; the guardian admits its orders from the deployed source (D27)
- Every driver order carries a measurable CPU/timing budget before SWE.1 is placed (D28)
- Comparisons are metrics only (present = a real value; categories not reported are never zero); forbidden reference names are kept as salted digests (D29)
- A rerun after a comparison names guarded metrics from the baseline run and reports each as PRESERVED or REGRESSED (compare --preserve) (D34)
- A rerun names its predecessor runs (carry_from); requirements still valid for unchanged inputs keep content and PASS verdict, only those the findings name are reworked (D37)
- The set inspection of a functional order reads the attributes as a residue index beside the requirements markdown (values the markdown does not state), so a large set fits the context (D39)
- Requirements cite each other by key and the assembly writes the current id; no authoring-process text; work-order budgets are mandatory, measured requirements and the introduction states that policy (D40)

## Per-order settings

- The SWE.1 level (functional or register) is a versioned per-order setting; an order without it stays register-level (D6)
- The scope is the full delivered public API limited by the order's scope rule; everything else is recorded as delivered out of scope or not delivered (D8)
- A functional order carries its scope rule under the work-order key scope_rule, beside the declared scope text (D14)
- Functional SWE.1 template v2 (design constraints one per topic and capped per guideline part, operations attribute with derived allocation, preconditions required) is selected per order by template id; v1 unchanged (D35)

## Pilot-only (not proposed)

- Functional orders refuse SWE.2 and later until those phases are defined for the functional level (D12)
- The pilot is built on the deployed owner-lane commit, without the held ladder SWE.3 work (D13)
- Functional packets offer no lessons until the lesson store holds functional-level lessons (D22)
- A pilot lineage restarted after an intake toolchain fix moves to a new series with new order names; earlier attempts stay history (D30)
- Each comparison round of the pilot runs as a new lineage series carried from the previous local and cloud runs (D38)
- The pilot accepts its first SWE.1 that passes both inspection phases; count differences to the benchmark are recorded, not forced (D41)

## What the ladder drivers would need

- the ladder runs one lineage per layer (LL, then HAL on the LL basis); adopting this merges each LL/HAL pair into one module lineage and retires the cross-lineage basis (D3)
- the register-level content of today's ladder SWE.1 must move into SWE.3 unit specifications, which needs the held ladder SWE.3 stage first (D5)
- each ladder order needs a scope rule (in / out / not delivered) so the inventory can classify its delivered API (D7)

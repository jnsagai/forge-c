# Owner-selected bounded repair in a QM pipeline demonstration

On 2026-10-30 the owner requested full-pipeline execution without development quality constraints stopping it,
then agreed to author correction loops on review/tool findings followed by continuation with remaining findings.
Standing signing delegation remains recorded separately for exact live source/profile/mission scopes.

The opt-in `qm-pipeline-demonstration-repair-v2` policy permits two phase repair cycles. Every cycle returns to
that phase's engineering/test author, reruns its ordinary verification and inspection, and keeps prior evidence.
Structured tasks have at most nine calls across the whole phase history (three visits, each with at most two
local answer repairs). Re-entry, changed input and crashes do not refill counters. A passing phase advances
immediately. After two repairs, a failing phase records an advisory gap and advances, even if no baseline exists.
All six phases are attempted; absent downstream inputs remain explicit failures, never fabricated artifacts.

Existing admission, mission accounting, one inference lease, native reconciliation, role permissions and
authenticated operator controls remain authoritative. No competing scheduler, memory store or quality authority.
Quality verdicts are unchanged. Every final package remains demonstration-only and unaccepted.

A HAL demonstration may import an unchanged, hash-bound LL header from a completed QM demonstration when every
phase has an attempt snapshot and the current SWE.3 baseline seals that header. The import records all six actual
gate dispositions and marks the component provisional. Strict/formal imports still require six passing gates.
The destination must also explicitly select QM demonstration execution; this never promotes the source product.

This is development execution policy, not a safety approval, product acceptance, performance allocation,
model-capability qualification or measured autonomy/availability result.

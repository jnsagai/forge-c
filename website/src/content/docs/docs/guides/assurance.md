Forge-C produces **safety-oriented engineering workproducts**. It does not itself approve a safety case, qualify a tool, authorize a deviation, or grant release authority.

## Work-order scope matters

The original RCC pilot records a QM development scope with no safety allocation. Other examples have different input and disposition histories. Read the work order, recorded owner decisions, assurance profile, and package limitations together.

A passing configured profile is not an ASIL determination. The [assurance-profile decision](https://github.com/jnsagai/forge-c/blob/main/docs/adr/ADR-0010-assurance-profile-vs-asil.md) explains this distinction.

## Enhanced AI software assurance

Feature 006 adds explicit assurance mechanisms and evidence handling, including verifier integrations and independence boundaries. Its name is a project feature label, not a claim of aviation regulatory approval.

Use the [assurance operations guide](https://github.com/jnsagai/forge-c/blob/main/docs/assurance/OPERATIONS.md), [assurance case](https://github.com/jnsagai/forge-c/blob/main/docs/assurance/ASSURANCE-CASE.md), and [recorded implementation status](https://github.com/jnsagai/forge-c/blob/main/docs/assurance/EASA-STATUS.md) to examine what was implemented and verified at the recorded revision.

## External authority

Human or organizational authority is required to accept safety-related deviations, confirm independent review, assess tool confidence or qualification, and authorize production release. The runtime's unattended execution does not remove those obligations.

Licensed standards and MCU publications remain outside the website. The site publishes no normative ISO or MISRA text and no licensed manual excerpts.

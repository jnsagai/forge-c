# Forge-C deployment recipe (feature 017)

This recipe builds Forge-C in two tiers. The same files build both the Omniverse2 mirror and production.

```text
   factory machine (VM, no GPU)                    model tier (GPU host, shared by many tenants)
  ┌──────────────────────────────┐   model channel  ┌───────────────────────────────────────────────┐
  │ Fabro + agents + tool servers│  HTTPS + API key │ tenant gateway: keys, shares, identity, swaps │
  │ LLM gateway (external mode) ─┼─────────────────►│  └─ engines: one model on the GPU at a time,   │
  │ supervisor, dashboards       │                  │     the others kept warm in host RAM           │
  └──────────────────────────────┘                  └───────────────────────────────────────────────┘
```

- **The factory knows tenants, never engines.** It names a model in each request. It never starts, stops or swaps a model, and it never sees a GPU.
- **The model tier knows tenants, never factories.** Any number of factories and other applications can share it, each with its own key and share.
- **The interface between them** is `specs/017-model-service-split/contracts/model-channel.md`. It is the only thing the platform team must provide.

## Files

| Path | Content |
| --- | --- |
| `params/omniverse2.yaml`, `params/production.yaml` | Every site-specific value, with its production counterpart. A production value with `confirmed: false` is still open with the platform team |
| `recipe.lock.json` | Pinned fingerprints: engine image digests, every model file's SHA-256, the identities of the served models, and the factory and tool versions |
| `fetch-artefacts.sh` | Downloads and pins the artefacts for a site (no GPU) |
| `model-tier/catalog.yaml` | Models, engines, full-capacity settings, warm strategy and swap policy. Generated by `forge_factory.modelservice.catalog_gen`, never edited by hand |
| `model-tier/compose.yaml` | Engine containers (vLLM). Bound to loopback; request logging off; digest-pinned |
| `model-tier/tenants.example.yaml` | Tenants: key hash, share, priority, allowed models |
| `model-tier/tenant-gateway.service`, `gateway.Dockerfile` | The tenant gateway as a host user unit, or as a container image |
| `factory-machine/` | Provisioning script, cloud-init, container stand-in, VM launcher |

Secrets never appear here. Configuration refers to them by name, and they are resolved from a private file (mode 0600) outside the repository.

## Build Omniverse2 (the mirror)

1. `deploy/recipe/fetch-artefacts.sh /mnt/data/forge-c/model-service`: pins vLLM, Qwen3.6-35B-A3B-FP8, the Ornith GGUF already on disk and the Ubuntu image.
2. `python -m forge_factory.modelservice.catalog_gen --profile <owner-lane profile> --lock deploy/recipe/recipe.lock.json --params deploy/recipe/params/omniverse2.yaml --out deploy/recipe/model-tier/catalog.yaml`
3. Create the secrets file and `model-tier/tenants.yaml`. The yaml holds hashes of the keys, never the keys.
4. `python -m forge_factory.modelservice.recipe verify --site omniverse2`
5. Start the model tier. **On Omniverse2 this happens only inside a qualification window** (`python -m forge_factory.modelservice.window run ...`), because the owner lane owns the GPU until the owner approves the cutover. `recipe apply` refuses outside a window.
6. `python -m forge_factory.modelservice.recipe drift --site omniverse2` checks a running environment against the lock.

## Build production (the same recipe)

1. The platform team provides the model channel: an OpenAI-compatible `/v1/chat/completions` and `/v1/models` over HTTPS, a per-tenant API key, and a tenant share for Forge-C.
   - Running their own copy of `model-tier/` is optional: any service that meets the contract works.
   - Optional: the `/forge/v1/identity` extension makes the served model attested. Without it, identity is inferred and the qualification report says so.
2. Fill `params/production.yaml`. `recipe plan --site production` lists every value that is still `confirmed: false`.
3. Build the factory VM with `factory-machine/cloud-init/user-data.yaml`, on the stock Ubuntu 22.04 cloud image. The Packer template is an optional convenience: Packer is BUSL-1.1, and nothing at runtime depends on it.
4. Set the factory's `config/factory/model-service.yaml` to `mode: external`, with the channel URL, the credential name and the expected identities.

## Parameter mapping (Omniverse2 against production)

`python -m forge_factory.modelservice.recipe plan --site omniverse2` prints the full table. The main differences:

| Parameter | Omniverse2 | Production |
| --- | --- | --- |
| GPU | RTX 6000 Ada, 48 GB | H200, 141 GB |
| Reference model precision | FP8 | BF16 |
| Context per sequence / sequences | 65,536 / 2 (measured in the first window) | 262,144 / 11 |
| Models on the GPU | one at a time, swapped in seconds from host RAM | platform's choice (co-resident or swapped) |
| Factory machine | container stand-in until the `kvm` group is granted, then a VM | VM |
| Channel | HTTP on the host loopback | HTTPS, internal CA if needed (to be confirmed) |
| Authentication | bearer key per tenant | to be confirmed by the platform team |

## What the Omniverse2 build does not prove

- **BF16 precision.** FP8 is used; quality equivalence is measured by the qualification report, not assumed.
- **Production scale:** 11 concurrent sequences, a 262k context and a 761k-token KV cache.
- **The platform team's actual serving stack and authentication.** Only the model-channel contract is relied on.
- **A real VM boundary while the container stand-in is used:** a separate kernel, the VM network stack and VM memory limits.
- **Co-resident models.** On 48 GB one model is on the GPU at a time and the service swaps.

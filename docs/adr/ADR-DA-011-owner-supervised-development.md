# ADR DA-011: temporary owner-supervised development

Date: 2026-11-05. Status: proposed implementation; runtime qualification and acceptance remain unproven.

The owner directed, “for now go on without needing signatures”. This authorizes a bounded external engineering channel while the signed production ACT branch and its signature verification remain unchanged. Outputs explicitly carry `OWNER_SUPERVISED_DEVELOPMENT`, `qualification_only=true` and `UNACCEPTED`. No fixture establishes model competence, safety approval, human MISRA review or task acceptance.

The channel uses the existing Placer, queue, MissionLedger, Executions, provider/request admission and role-approved MCP/Skills gates. It retains the original mission identity and accounting, including the first PRODUCT attempt and 1,048,576 tokens charged with unknown actual usage. Only original B/C/D orders remain eligible; profile, policies, model/role envelopes, quality requirements and all non-time caps are fixed. Any mission deadline amendment still uses the separate existing signed deadline operation. Runtime product and recovery wall budgets remain unchanged.

An external OS-owner process in the initial user namespace creates a private immutable record, anchors its digest in the existing protected Store authority table, and remains alive as its Unix-socket guardian. Production agents have no issuing MCP operation. Every new authority use verifies the original Store inode, record digest, original socket inode and live challenge, Intent RUNNING epoch, source/control/mission identity and fixed expiry. A job remains bound to its issuing guardian lifetime; another record cannot silently authorize an existing job. STOP, guardian loss, source changes or uncertain identity refuse new effects. Existing uncertain native/request leases settle only through normal durable observation and provider-quiescence rules.

Trusted provider creation passes pre-opened readonly kernel proc identity files and the original socket node into a narrow private view. Actual nested PID/user-namespace tests established that nsfs bind mounts are unavailable in this environment; no snapshot substitutes for them. The private verifier instead requires exact procfs mount roots for original guardian stat/uid_map, original start/boot identity, the entire initial-namespace UID-map extent, the actual provider user/PID namespace and protected Store/socket bindings. An observer in a mapped user namespace can see the initial map's outside start as the invalid-UID sentinel 4294967295. This rendering is described by [user_namespaces(7)](https://man7.org/linux/man-pages/man7/user_namespaces.7.html); only the measured full-range extent is accepted. Real mapped children have a one-UID extent and cannot mint the required full range. A separate mapped-host route requires the original visible guardian PID in peer credentials and the original PID namespace; PID zero alone never authorizes anything.

All selected-lane agent-controlled executable artifacts, including compiled C test binaries, run through existing scoped Bubblewrap isolation with separate PID/user/network views and no control socket, host proc, guardian HOME or writable authority mounts. Missing isolation refuses execution. Normal production command paths retain their previous behavior. The OS owner and root are trusted external engineering principals; arbitrary host code run directly by those principals is outside the confined-agent threat boundary.

Before Placer admission or attempt spend, provider readiness distinguishes absent, compatible, known retirement required and unknown. Existing providers without this guardian view are not silently reused. Record issuance remains possible while replacement is needed, so the guardian can stay alive during separately authorized normal exact-owner, quiescent provider retirement. The development loop performs no automatic replacement and never assumes idle from GPU utilization alone.

A one-time independent UTC bracket, with same-RPC BOOTTIME sampled before MONOTONIC, is converted to a conservative same-boot monotonic deadline at issuance. Its short freshness bound applies only to issuing the record, using both sampled clocks so a suspend before issuance cannot stretch that freshness. Later calls require the same boot and fixed monotonic deadline plus a conservatively derived CLOCK_BOOTTIME deadline that includes suspend, without recurring external time or synchronization requirements. Reboot, missing/invalid witness or exhausted deadline refuses. This neither extends the owner-fixed 2026-11-19T03:07:06Z deadline nor changes normal mission/authz expiry checks.

The production OBSERVE conductor continues writing its own unchanged feed/heartbeat. The external development producer uses a separate private audit/heartbeat and existing durable jobs; it never claims the production systemd unit's PID or ACT mode. No live deployment, model/GPU execution or acceptance follows from this ADR or private controls.

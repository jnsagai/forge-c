# Explicit read-only launch guard for supervised development

Status: proposed implementation; no live activation or feature-completion claim.

The owner directed “for now go on without needing signatures” on 2026-11-05. The temporary supervised-development lane keeps the original finite mission, recorded spend and unknown usage, model/role envelopes and quality gates. Signed production ACT remains unchanged. This guard does not issue authority or accept a product, model role, MISRA review or safety claim.

The deployed legacy engineering guard has two incompatible assumptions: it requires the separate production conductor heartbeat to say PILOT, although that conductor deliberately remains healthy OBSERVE; and it compares NVIDIA compute PIDs with the nsenter waiter stored in the old process projection, although a private provider has a distinct actual llama-server child. The real first supervised attempt stopped at this guard before native submission. Its attempt and token reservation remain spent. No order is reopened or refunded by this correction.

The repository now provides an explicitly selected host artifact, `factory/python/forge_factory/afo/owner_launch_guard.sh`, and its Python checker. The default legacy guard is unchanged. Future reviewed OS-owner configuration supplies FORGE_LINE_GUARD, FORGE_LINE_PYTHON, FORGE_OWNER_LAUNCH_GUARD_CONFIG and its exact SHA256. The checker imports ordinary authority/provider APIs from the explicitly selected qualified runtime, which may remain the prior source when this host artifact is staged separately. Its own file SHA is bound in the immutable configuration; it is never represented as part of an unchanged native source revision.

The guard retains both GPU queue emptiness predicates, both original operations-file hashes and refusal of every foreign GPU PID. It requires a healthy exact production OBSERVE unit/PID/invocation and fresh heartbeat, plus the current OS-owner guardian, its private OWNER_SUPERVISED_DEVELOPMENT/UNACCEPTED heartbeat and normal D.current validation. The latter retains canonical Store binding, original accounting and unknown usage, source/profile/policy/mission identity, live socket/kernel proof, Intent epoch and fixed same-boot MONOTONIC/BOOTTIME expiry. Healthy checks make zero model calls.

Worker ownership comes from the existing immutable managed-instance and worker proofs and actual PID/start/boot/namespace/NSpid/argv/parent identities. A caller argument is only a hint: it must equal the exact captured waiter or actual worker. A HOST-created proof uses P._bound_worker. A proof created by the exact captured outer mapped observer may encode UID0; the checker requires the v2 outer holder’s live identity, captured one-UID map and exact USER/NET namespaces before comparing the corresponding host UID. This read-only observation does not relax provider signal/stop APIs. There is no generic UID, process-name, absent-probe or unknown-worker exception. The guard does not call capture_worker because that API writes ownership evidence.

Actual callers remain the external OS-owner M2 launcher on the host. The guardian/controller and native workflow still use the existing Store, leases, resource ownership, role SKILL/MCP and inference accounting. The shell entry is a non-AI host check, not a production-agent shell capability. Sandboxed candidates cannot obtain initial OS-owner namespace provenance or the private guardian context through this artifact.

Rollout remains separate engineering work: a new versioned unit/record and campaign data namespace, normal quiescence and exact managed-provider retirement, unchanged Intent epoch and all history, then a fresh bounded issuance witness. The failed B attempt remains recorded; only genuinely unused C/D slots may be selected by the normal planner under the existing four-attempt cap. No live unit, authority, source, queue, process or policy is changed by implementing this artifact. Repository-owned default deployment selection and full 014 runtime qualification remain open.

# ADR DA-012: explicit managed profile bootstrap in owner-supervised development

Status: implementation candidate; qualification and actual runtime acceptance remain unproven.

Full retirement removes Fabro as well as the legacy provider. The existing development producer then correctly treats an unreachable native API as busy. Generic managed startup uses the distinct Conductor database, which is absent on this line; automatic profile recovery separately requires CRE authority that is not enabled. Neither database fabrication nor changing that policy is a valid startup recipe.

The explicit optional `--bootstrap-managed-profile` stage runs after the normal development guardian is issued and before the first Placer cycle. Only that same initial-host OS-owner issuer may use it. It intersects the existing original B/C/D `launch_workorder` and `line_stack_restart` scope, bound control, measured native binary, unchanged fixed profile, canonical line Store, mission and Intent. No job, attempt, token reservation, grant, policy or deadline is created by bootstrap. Ordinary signed production startup and automatic CRE recovery retain their existing behavior.

The coordinator takes Intent, then nonblocking GPU, stack and existing ACT locks; the Intent acquisition is also nonblocking. The same Placer retains ACT across startup into its ordinary loop. Canonical inference owners, unreleased execution leases, nonquiescent requests and unresolved outbox states refuse; historical PAUSED orders and terminal FAILED/QUARANTINED commands are preserved. Only known quiescent recorded and surveyed lifetimes may be replaced; unknown kernel state refuses.

A read-only five-table native SQLite checkpoint validates the known 0.362 columns/primary keys and known terminal states before any process starts. Typed, schema-bound logical fingerprints preserve complete native history without exporting payloads. Fabro and its loopback relay start first; complete archived/removing API inventory must match that storage checkpoint before gateway/model startup. Full provider readiness includes llama-server and same-guardian provider compatibility, followed by unchanged native history and canonical quiescence. Loading the configured model server is a prospective GPU effect; bootstrap performs no inference or work-order dispatch.

Authority is fresh at every physical process boundary. Potentially blocking authorization and guardian challenge precede a final Intent, input/binary, cancellation and both MONOTONIC/BOOTTIME deadline check. The fixed guardian expiry remains the original independently witnessed deadline; startup additionally has an effect budget of at most600 seconds. Bounded I/O or complete history observation may overrun the requested return budget, but no new effect is permitted after expiry. SIGTERM during startup reaches the same cancellation event as the main loop.

An intent is committed before process effects and a result is appended; neither overwrites history. Partial or unknown startup closes that issuing guardian and records reconciliation required, without signalling unknown processes or releasing a lease. An unresolved prior attempt blocks a fresh issuer from silently retrying. No private control establishes actual role competence, safety review, production ACT, endurance acceptance or task completion.
